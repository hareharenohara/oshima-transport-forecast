# 就航予測AIの入力・判断処理の再設計案

作成日: 2026-10-07。設計案のみ。予測コード・ML・公開環境への反映は行っていません。

## 目的と範囲

便ごとの就航見込みを維持し、AIに用途未定義のデータを一律に送る方式をやめる。対象はAI入力だけで、既存MLの特徴量と元データ取得は変更しない。

容量設計は当日〜4日先の各日10便、合計50便を標準にする。既存の28便・31便の試算を50便の保証値として使わない。

## 処理の構成

1. 公式状態と更新時刻から再評価対象を選ぶ。
2. 対象便に適用できる公式基準・公開経験則を選ぶ。
3. 選んだルールが必要とする地点・時間・変数だけを抽出する。
4. プログラムで公式基準の比較、欠損、モデル差、前回からの重要変化を計算する。
5. 共有ルール・共有根拠を一度だけ含め、便ごとの参照を付けて120bに直接渡す。20bの文章整理は省く案とする。
6. AIは与えられた根拠と、別途確定するS〜D統合ルールで評価する。
7. 確信度・表示用の基準一覧・更新日時をプログラムで付ける。

S〜D統合ルールと確信度の具体的な算出条件は未確定。AIの自由な重み付けで埋めない。これらが確定するまで新方式の実運用を始めない。

## ルールの登録方法

各ルールにはID、出典・版、用途（就航／港／確信度）、船種・航路・方向、対象地点と時間窓、必要変数、適用条件、評価への作用、状態を登録する。

状態は「適用可能」「条件定義待ち」「必要データなし」「対象外」を区別する。「適用できない」は「懸念なし」ではない。

登録済み公式基準はユーザー提供マスター仕様に基づく。原文と適用範囲の再照合を実運用前の条件とする。出港停止・航行変更・航行停止の用途を区別し、異なる船種や港へ転用しない。大島入港基準を大島出港へ自動転用しない。

中村氏の登録内容は公式基準ではなく公開経験則として扱う。「強い西風」「高いうねり」「穏やか」「7〜8m/s」等は現状の登録だけでは適用条件・作用が十分でない。独自の数値境界を作らず、必要な原文確認と条件整理が完了するまで判断への反映を保留する。

## 入力項目の対応

|項目|就航判断への用途|新入力での扱い|
|---|---|---|
|風速|対象船種・港・航路の公式比較、相模灘の経験則|該当範囲だけ残す。突風を通常風速の基準へ代入しない|
|波高|対象船種・港・航路の公式比較、相模灘の経験則|該当範囲だけ残す。風浪・うねり高さを総波高と取り違えない|
|風向|南西風・北東風・西風の航路別経験則|該当地点・時間の風速や海況と対応させて残す。適用条件未定義時は推測しない|
|うねり高さ・方向|岡田側へのうねり等の経験則|関係地点・時間に限定。経験則の条件・作用が確定した場合に使用|
|波向|うねり方向とは別変数|使う経験則の変数定義が確認できる場合だけ残す。うねり方向の代用にしない|
|降水量|登録上は港選択の経験則|就航判断の入力から省く。港予測を行い、適用条件を定義できた場合だけ港用入力へ追加|
|気圧|採用済みの作用なし|AI入力から省く|
|突風|専用分析では候補だが採用基準なし|AI入力から省く案。検証して作用を定義した後に追加可能|
|風浪高さ・方向・周期|採用済みの個別作用なし|AI入力から省く案。総波高は保持する|
|波周期・うねり周期|現在の登録には具体的な使い方なし|AI入力から省く案。一般知識だけで重みを付けない。周期を必要とする経験則・検証済み関係が確認された場合は追加|
|全項目の3・6時間差|一律の適用ルールなし|一律送信をやめる。経験則が必要とする時系列を用途別に保持|
|前回AI評価|当該便の新しい気象根拠ではない|新規判断入力から省く。再利用判定にプログラム側で使用|
|既存MLの平均・最小・最大等|AIへの反映方法が未定義|新AI判断入力から省く案。既存MLの計算・表示は保持|
|専用MLの項目分析|全項目review_required、汎化性能に課題|判断ルールに採用しない。分析成果物として保持|
|予報先・取得時刻・欠損・モデル差|確信度と有効性判定|プログラムで計算。AIには判断可否と必要な不一致・欠損だけ渡す|

「省く」は運航上不要という断定ではなく、現時点でAIに反映する根拠が定義されていないという扱い。情報がないことから安全・危険を補完しない。必要なルールが増えれば入力も増える。

## 失ってはいけない対応関係

- 値、変数、単位、モデル、地点、時刻／時間窓を対応付ける。
- 公式比較の最大値には、その値が出た地点と時刻を残す。
- 風のピークと波のピークが別地点・別時刻なら、別の根拠として保持する。同時発生とは表現しない。
- 風向の経験則には、その方向が出た時刻の風速・波等を対応付ける。別の時間の最大値と無条件に組み合わせない。
- モデル間の最大値・最小値だけでは方向や同時発生の関係が失われる場合がある。圧縮目的だけでモデルを混ぜない。
- 予報地点の値は港内の実測ではない。取得元地点・海洋グリッドが同じ岡田／元町の制約を記録する。
- 時系列を必要とするルールには変化点・継続時間等の定義が必要。3時間差・6時間差だけで代用しない。
- 視程・台風情報・吹送距離等が必要なルールは、未取得の状態を明示し、別変数から捏造しない。

## リクエストの構成

全知識の全文ではなく、そのリクエストに必要なルール定義だけを共有する。ルールIDだけではAIに意味が伝わらないため、必要な条件と作用は同時に渡す。

共有の根拠テーブルには必要な数値・位置・時間・モデル・単位を保持し、便は必要な根拠IDを参照する。同一モデル・同一地点・同一時間窓・同一集計の完全一致情報だけを共有する。似ている便を同一条件として扱わない。

基準比率や状態を計算可能な場合はプログラムで計算し、予報値・基準値・比率・説明文を複数箇所へ繰り返さない。欠損をゼロとしない。

概念例（形式例であり、実際の判断・数値・完成スキーマではない）:

```json
{
  "rules": [
    {"id": "jet_route_wave", "purpose": "operation", "threshold": 3.0, "unit": "m", "effect": "concern_on_reaching"}
  ],
  "evidence": [
    {"id": "e1", "rule": "jet_route_wave", "model": "モデル名", "location": "地点ID", "time": "予報時刻", "value": 3.2, "status": "reached"}
  ],
  "services": [
    {"id": "便ID", "ship": "jet", "route": "東京", "direction": "to_oshima", "departure": "出発時刻", "arrival": "到着時刻", "evidence_ids": ["e1"], "unresolved": ["visibility"]}
  ]
}
```

実際の公式ルール定義は適用範囲や注意事項も含める。根拠ID・入力項目の対応を確認できる監査情報はプログラム側に保存する。

## AI出力

便ID、評価可否、S〜D（評価不能は別状態）、主な根拠ID、短い説明を基本にする。港予測は別用途の根拠と別フィールドで扱い、港判断の不確実性を就航判断へ無条件に混ぜない。

確信度、公式基準状態一覧、更新日時、再利用状態はプログラム側で付与する。既存画面との互換性が必要な表示項目はAIの同内容再生成ではなく既存出力への変換で対応する。変換ルールは別途定義する。

## 更新対象

|日付|AI評価の周期|
|---|---|
|当日|公式★のみ。2時間おきを試算上の仮定とし、最終確定が必要|
|翌日|2時間|
|2日先|4時間|
|3日先|6時間|
|4日先|12時間|

当日〇・×は予測を生成せず公式状態を表示。未取得・不明を〇・×として除外しない。★へ戻った便、重要条件が変わった便は再評価候補とする。臨時更新分も予算管理する。

基準時刻はJST。日付が変わった時点で新しい周期に移行し、最終成功更新からの経過時間で期限切れを検出する。更新失敗で次回まで古い評価を有効扱いしない。AI対象から除外しても公式状態の取得更新は継続する。

50便固定なら、翌日〜4日先の延べ評価は10×(12+6+4+2)=240便/日。当日★がk便なら12kを追加する。全便2時間更新の600便/日と比較すると、当日★0/2/10便では240/264/360便/日。ただし共通入力と出力予算があるのでトークン量はこの比率に比例しない。

## 上限に達しても更新全体を止めない

気象取得・既存ML更新の保存はAI完了を待たない構成に分離する。AIの失敗・待機で全体更新が失敗しないことを実装時に検証する。

毎分・日次の実枠と使用量に基づき、入力・推論を含む出力・再試行を予約する。同時実行間で予算を共有し、他用途を考慮する。1リクエストの便数は固定ではなく、必要情報と出力が収まる範囲で決める。

AIが更新できない場合は、前回評価の有効性を判定し、表示時刻と更新待ちを付ける。重要変化後・期限切れは流用しない。最新AI評価も必ず生成するという要件は別途利用枠と実行期限で保証可能か確認する。

## 実装前の確認事項

1. 公式基準・経験則の原文、適用条件、作用の確認。条件不明の経験則を無理に採用しない。
2. この入力選択に対して、重要な場面で必要情報を落としていないか確認する。
3. S〜D統合ルールと確信度の算出条件を定義する。
4. 50便で、当日★0/2/10便と荒天の臨時更新を含むトークン試算を行う。
5. 生成結果の便漏れ・JSON不一致・不足情報の推測・判断品質を検証する。
6. 変更内容を確認してから予測コードへの実装と公開反映を行う。
