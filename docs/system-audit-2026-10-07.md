# システム全体の確認結果

2026-10-07 16時頃～16:13 JSTの公開環境とローカルを確認しました。公開Workerは `1bb0f685-e15e-4129-80ad-d8ff15b49fb7`、プロンプトv17です。本確認では業務ロジックの変更・デプロイ・DB書き換え・手動AI生成・通知送信を行っていません。

## 結論

ページ、保存済みデータの読み取り、定期起動、ML計算と保存は動作しています。ただし、予測対象の網羅性、利用するモデル数、AI結果の採用、コメント品質、ダイヤ自動更新に実際の問題を確認しました。全体正常とは判定できません。117件のテストが成功していても、以下の実運用条件を十分に検証していませんでした。

## 優先して直す問題

### 1. 短時間便が予報データ不足と誤判定される

翌日10/8の熱海1100便（09:10～09:55）は最新15:30更新でもAI unavailableです。保存理由は「重要な気象・海象データが不足しており、AI評価できません。」です。

`src/forecast/judgment-context.ts:45` の phase は開始～終了の内側の毎時予報だけを対象にします。この45分の区間には毎正時が一つもなく、09:00と10:00のデータが正常でも route の全変数が null になります。全11地点・全５モデルに完全な毎時データを与えるローカル検証でも、出港風速5、航路風速null、航路波高null、入港風速5、assessable=falseを再現しました。相模灘の経験則比較にも同じ抽出方法を使っています。

新しい集約処理にも区間内抽出があり、元の便別判断が不成立だと枠全体もAPI送信前に対象外になります。短時間便の前後の毎時値をどう対応させるかを定義して、便別判断と集約処理を揃える必要があります。無条件の０補完で解消すべきではありません。

### 2. JMAとECMWF海況がモデル全体として除外される

現在のソース取得を読み取り実行した結果は気象ECMWF IFS・GFS、海況GFS Waveの３ソースだけでした。公開16:00実行のML保存も５便×２組み合わせ＝10行でした。

| モデル | 実際の失敗 | 取得APIで確認した値 |
|---|---|---|
| JMA MSM | wind_gusts_10m[0] missing | 東京地点120時間中、風速・風向等88時間有効、突風０時間有効 |
| ECMWF WAM | wind_wave_height[0] missing | 東京地点の総波高・波向・周期は120時間有効。風浪成分とうねり成分は０時間有効 |

`src/forecast/open-meteo.ts:32` はいずれか一つの要求変数・地点・時間に欠損があると全体をthrowし、`multi-model.ts` がそのモデルを除外します。HTTP200の取得でも、使える風・総波高まで失われます。JMAには予報期間の限界もあり、全５日を完全データとする要求と合いません。

モデルの比較材料とMLの組み合わせ数が減っています。ただし、MLには突風・海況成分の入力契約があるため、単に欠損を通すだけの変更はできません。AIに利用できる部分データと、MLで安全に利用できる入力を区別する設計が必要です。

### 3. 公式ダイヤの自動取得が公開環境で失敗する

16:10の自然な定期実行をログで観測し、各対象日で以下のエラーを確認しました。

`TypeError: Illegal invocation: function called with incorrect this reference`

`src/schedule/official-timetable.ts:233` の `this.fetchFn(...)` は、渡された実行環境のfetchをクラスメンバーとして呼びます。Workers上のthis参照の不整合が有力な原因です。公開環境のエラーは確定、該当呼び出しが原因という特定はコードと実行差に基づく推定です。[Cloudflareの該当エラー説明](https://developers.cloudflare.com/workers/observability/errors/#illegal-invocation-errors)も呼び出し時のthis参照を確認するよう説明しています。

同じコードをローカルで公式サイトへ接続すると、各HTMLはHTTP200で10/7～11の27便を取得できました。公式サイトが現在取得不能なのではありません。

最新の成功した同期記録は10/6 16:29頃の手動復旧。保存済みの有効ダイヤは10/20まであり、現在の予測処理はそれを使って継続しています。自動更新の復旧までは、ダイヤ変更の追随と保存範囲より先の日付にリスクがあります。

当日の公式運航状況の取得は別経路で動いています。ただし公式注記にある臨時大型3001便は、今回取得した当日の一覧には含まれていません。定期ダイヤと臨時便の取り込みの範囲は別途整理が必要です。

### 4. ４日先のAI回答が検証で拒否され、そのまま評価なしになる

10/11のジェット４便・大型１便をまとめた16:00実行で、両評価枠ともAI unavailableを確認しました。APIはHTTP200、finish_reason=stop、要求IDと返却IDは２件とも一致し、使用量は入力3,079＋出力1,033＝4,112です。トークン超過、途中終了、JSON不一致、枠の返却漏れではありません。

保存理由は両方とも `S is not supported: concerns, missing data or model disagreement`。AIが返したS評価がプログラム側のS条件を満たさず拒否されたことが原因です。

現在はポリシー違反を各結果の unavailable にして終了するため、許容される評価での再判断処理には進みません。APIに伝える選択可能なランク制約と、条件違反時の扱いを整理する必要があります。Sの条件自体を緩めたり、根拠なくAなどへ置換して解消すべきではありません。

### 5. A評価に「評価保留」というコメントが採用されている

10/8の15:30更新では６便のうち５便がgenerated・A、１便は問題1のデータ不足でした。generatedの５便は assessment と summary がすべて「評価保留」、港理由も空でした。公開ブラウザでも東京1220便のA評価と総合コメント「評価保留」を確認しました。

AI回答のJSON形式は正常でも、評価とコメントが矛盾し、具体値・基準比較・判断理由がありません。コメントの自然さや納得できる根拠を求めるプロンプトに対し、結果を受け入れる検証が不足しています。これは今回v17より前のv16生成結果です。v17の通常便でも改善したと確認できる証拠はありません。

## 運用・画面・通知で確認した問題

### AI不成立が実行成功として記録される

上記16:00実行は `completed / target_count=5 / success_count=5 / error_count=0 / forecasts=ok` と記録されています。success_countは保存成功の数であり、AI生成成功の数ではありません。２枠ともAI不成立でも正常実行に見えるため、監視に使うと見逃します。

日付カードの「最終更新16:00」も、その日のAI判断が成功した時刻とは限りません。今回の失敗は一覧では「評価待ち」、詳細では「AI評価を取得できませんでした。」と表示され、初回未生成と失敗を一覧で区別できません。

### 自動再読込で展開状態が失われる

画面を操作中、開いた日付カードが再び折りたたまれることを確認しました。`src/ui/assets.ts:16` は最大60秒でloadを再実行し、`:20` のrenderが展開状態を保存せず全カードをcollapsedに再生成しています。詳細ウィンドウ自体が閉じるという確認ではありません。

### 集約評価の港変更が通知処理に渡らない

`readRunPushAssessments` は便別ai_predictionsとMLだけを参照し、group_forecastsを参照しません。２日先以降は便別AIを空にしているため、集約評価の港変更があっても、その港を比較する通知経路がありません。コード上で確認した未対応です。実際の通知送信は今回行っていません。

公式状況更新の通知フラグも保存されていますが、通知イベント判定では利用されていません。これは画面の新規チェック項目を確認したという意味ではなく、既存の保存契約と実行処理の不一致です。
